# Release — able-rest-api Framework 1차 정식 릴리스

현재 Framework Phase 1~6이 완료된 상태다.

이번 작업에서는 **버전을 올리고 정식 릴리스까지 완료**하라.

## 작업 순서

1. 현재 버전 관리 방식과 기존 tag/release 이력을 확인
2. 이번 Framework 1차 완료에 적절한 버전을 결정
   - 기존 버전 체계를 우선 유지
   - 명확한 breaking change가 없다면 기존 정책에 맞는 minor/patch 선택
3. 코드·README·문서·빌드 스크립트 등에 버전 값이 있으면 일관되게 갱신
4. 변경 내역을 요약한 release notes 작성
5. 최종 검증
6. 버전 변경 커밋
7. Git tag 생성 및 push
8. GitHub Release 생성

## Release Notes에 포함

간략히 다음을 정리한다.

- OpenAPI 3.x Single Source of Truth
- runtime/semantic/side-effect contract 검증
- CI OpenAPI Gate
- module 기반 Framework 구조
- user/mail/scheduler 모듈 분리
- 영속 예약 메일
- retry/claim/concurrency 처리
- 안정적인 Message-ID/멱등성 대응
- 주요 security hardening
- 알려진 제한사항
  - SMTP exactly-once 자체는 보장하지 않음
  - 운영 DB migration 별도 적용 필요
  - 미검증 DB가 있으면 명시

## 최종 검증

최소 다음을 모두 실행한다.

```bash
go test ./...
go test -race ./...
go vet ./...
go build ./...
make openapi-check
git diff --check
```

CI workflow가 있다면 tag push 후 실제 CI/Release workflow 결과도 확인한다.

실패한 상태에서는 tag/release를 생성하지 않는다.

## Git 처리

릴리스 전 작업 트리를 확인하고 `docs/reference_docs/` 등 기존 미추적 참고 파일은 커밋하지 않는다.

버전 변경 및 필요한 문서만 커밋한 뒤:

```text
release: vX.Y.Z
```

형식의 명확한 커밋을 만든다.

그 후 annotated tag를 생성한다.

```bash
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin <branch>
git push origin vX.Y.Z
```

기존 branch 이름과 tag 이름이 충돌하는 경우 먼저 ref를 확인하고 안전하게 처리한다.
